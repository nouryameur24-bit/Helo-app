1. SÉCURITÉ API & SECRETS
═══════════════════════════════════════════════════════════════

- Vérifier qu'AUCUNE clé API n'est hardcodée dans le code source. Toutes doivent venir de process.env.
- Créer lib/config.ts qui centralise TOUS les accès aux variables d'environnement :
  export const Config = {
    supabaseUrl: process.env.EXPO_PUBLIC_SUPABASE_URL ?? '',
    supabaseAnonKey: process.env.EXPO_PUBLIC_SUPABASE_ANON_KEY ?? '',
    googleVisionKey: process.env.EXPO_PUBLIC_GOOGLE_VISION_KEY ?? '',
    anthropicKey: process.env.EXPO_PUBLIC_ANTHROPIC_API_KEY ?? '',
    revenueCatKey: process.env.EXPO_PUBLIC_RC_KEY_IOS ?? '',
  }
- Remplacer tous les process.env directs dans le code par Config.xxx
- Ajouter une vérification au démarrage : si une clé critique manque → log warning (pas crash)

IMPORTANT — CLÉS API CÔTÉ CLIENT :
- La clé Anthropic (pour le chatbot) ne doit PAS être exposée côté client en production.
- Créer une Supabase Edge Function (supabase/functions/chat/index.ts) qui proxie les appels à Claude :
  * L'app envoie le message à la Edge Function
  * La Edge Function appelle Claude avec la clé stockée côté serveur (Supabase Vault ou env)
  * La Edge Function retourne la réponse à l'app
- Même chose pour Google Vision : créer supabase/functions/ocr/index.ts
- L'app n'a plus AUCUNE clé API tierce côté client, seulement la clé Supabase anon

2. SUPABASE ROW LEVEL SECURITY (RLS)
═══════════════════════════════════════════════════════════════

Vérifier et renforcer les RLS policies sur CHAQUE table :

- ingredients : SELECT pour tous (public, lecture seule). Pas d'INSERT/UPDATE/DELETE via anon.
- products : SELECT pour tous (public, lecture seule). Pas d'INSERT/UPDATE/DELETE via anon.
- scan_history : SELECT/INSERT/UPDATE/DELETE uniquement WHERE user_id = auth.uid() OU user_id match le header custom
- shopping_list : SELECT/INSERT/UPDATE/DELETE uniquement pour le propriétaire
- community_submissions : INSERT pour tous (soumettre), SELECT pour les approved, pas de DELETE/UPDATE via anon
- profiles : SELECT/UPDATE uniquement pour le propriétaire
- partner_links : SELECT uniquement si l'utilisateur est un des deux côtés du lien

Générer le fichier SQL complet : supabase/rls-policies.sql

3. VALIDATION & SANITIZATION DES INPUTS
═══════════════════════════════════════════════════════════════

Créer lib/validation.ts :

- sanitizeText(input): strip HTML tags, trim, max length 500 chars
- sanitizeBarcode(input): ne garder que les chiffres, longueur 8 ou 13
- sanitizeEmail(input): regex validation basique
- sanitizeName(input): strip caractères spéciaux dangereux, max 100 chars

Appliquer sur TOUS les inputs utilisateur :
- Champ prénom (onboarding)
- Champ recherche (search)
- Soumission communautaire (nom, marque)
- Messages chatbot
- Code partenaire

Aucun input utilisateur ne doit atteindre Supabase ou une API sans être sanitisé.
